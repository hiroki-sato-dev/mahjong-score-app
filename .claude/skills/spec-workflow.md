# スペック駆動開発ワークフロー

このプロジェクトはスペック駆動開発を採用している。実装前に仕様を書き、完了後にマスター仕様書へマージする。

## ワークフロー全体像

```
仕様作成 → 実装 → マージ
/spec-new  → コーディング → /spec-done
```

## spec.md の書き方

### 含めるべき内容

- **概要**: 1〜2文で機能の目的を説明
- **要件**: 機能要件（何ができるか）と非機能要件（パフォーマンス・セキュリティ等）
- **画面・UI**: 関連するコンポーネント・レイアウト。`docs/design/REFERENCE.md` のコンポーネントを参照
- **API・データ**: エンドポイント設計、型定義、Zustandストアの変更点
- **考慮事項**: バリデーション・エラーハンドリング・ロール制御

### 良い仕様の条件

- 実装者（自分）が迷わず実装できる粒度
- テストケースが想像できる
- 完了条件が明確

## tasks.md の書き方

- 型・ロジック → コンポーネント → ページ → テスト の順で記載
- 1タスク = 1コミット程度の粒度
- 完了条件に「テスト通過」「spec.mdと一致」を必ず含める

## SPEC.md へのマージ判断

マージしてよい条件：
- tasks.md の完了条件をすべてチェックできる
- テストが通っている
- 実装と spec.md の記述が一致している

マージ時の注意：
- SPEC.md のセクション構造を崩さない
- 既存仕様を更新する場合は古い記述を残さない
- マージ後に全体として一貫して読めるか確認する
